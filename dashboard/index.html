How we built our studio dashboard with Claude

₹0 a month. Two editors. No coding background needed to follow along.

Our whole studio runs on a dashboard we built ourselves: tasks, clients, hard drives, money in and out, leads, and notifications on our phones. Every project app we tried was either expensive or built for someone else's workflow, so we described ours to Claude and built it.

This is the full pipeline: what it does, the stack, the exact steps, and the prompts we'd use if we started again tomorrow.

From Cutcult, a post-production studio based in Keralam. Instagram: @cutcult.in

What it does

Screen What it's for
Today Opens every morning. Whose turn it is, what's coming up, what's late or waiting on a client, and who has how much work.
Tasks Every task as a list or a board: To do → In progress → Client review → Revisions → Approved → Delivered. Each task is split into steps (assembly, motion, sound, grade…), each with a person and a date. Tick a step and the next person gets "Your turn".
Clients Each client's playbook: formats, file naming, delivery, who approves, how many revision rounds. It shows on every task for that client.
Projects Each project's tasks, drives, invoices and expenses in one place.
Money Invoices and expenses in rupees, repeating subscriptions, CSV export for the CA.
Drives Every hard drive with a code and a printable QR label. Scan it with a phone to check it out or in. It warns when footage has no second copy.
Inbox Mentions, tasks for you, comments and due dates. Also arrives as phone notifications.
Notes, Pitch, Team Private notes, a leads pipeline, and team roles and permissions.

It installs on a phone or laptop like an app, but it's a website, so there's nothing to download or update.

You don't need all of this. Start with Today and Tasks. Everything else came later, one screen at a time.

The stack (and why)

Piece What it does Why we picked it
Claude Code Writes and edits the code, inside your project folder Not the chat window. It reads your whole project, edits the files itself and runs the build to check its work.
Git + a private GitHub repo Saves every version Every change is a commit, so you can always go back. Cloudflare deploys straight from it.
Cloudflare Worker One Worker serves the app, the API and the scheduled jobs Free plan, fast in India, one account for everything.
Cloudflare D1 The database Free, and it keeps 7 days of history, so a mistake can be rolled back.
React + Vite The app you see Fast to build, and Claude writes it well.
Hono The API inside the Worker Small, made for Workers.
Web app manifest + service worker "Install as an app" and phone notifications Works on Android, iPhone (Add to Home Screen), Mac and Windows.
Resend (optional) Emails: daily digest, "your turn", mentions Free for 100 emails a day.
Trello / Google Drive (optional) Sync with agency Trello boards, a Drive folder per client Only if you need them.

The pipeline, step by step

1. Write down how your studio actually works

Before any code. Plain English, one page. This is the most important step, and the one AI can't do for you.

Answer these:

  • What's a project, and what's a task? (Ours: one project per client brief, one task per batch, like "Batch 1 · 10 reels".)
  • What stages does a task move through? (Ours: To do, In progress, Client review, Revisions, Approved, Delivered.)
  • Who touches a task, in what order? (Ours: assembly → motion → sound → grade, each step with a person and a date.)
  • What do you forget most often? (Ours: which drive has which footage, which client is waiting on us, which subscription renews next week.)
  • Who should see what? (Ours: editors see their own tasks, the accountant sees money, clients see only their own work.)

If you can't explain your workflow in a page, no app will fix it. If you can, you might not need the app.

2. Set up the environment

  1. Install Node.js, Git and Claude Code.
  2. Make a folder, run git init, and create a private repo on GitHub.
  3. Put your one-page workflow in the folder as WORKFLOW.md.
  4. Open Claude Code in that folder.

3. Make the plan first, with a cheaper model

Planning doesn't need the most expensive model. Use a cheaper one to turn your workflow into a build plan, then review it yourself before anything gets built.

Prompt: Read WORKFLOW.md. Write PLAN.md for an internal studio dashboard: one Cloudflare Worker that serves a React app, a Hono API and a cron job, with a Cloudflare D1 database. List the screens, the database tables, who can see what, and the order to build them in, starting with the smallest useful version (a Today page and a task list). Ask me questions about anything unclear before you write the plan.

Read the plan like a brief. Push back where it doesn't match how you work. Expect it to change as you build: ours started with Supabase and ended up all on Cloudflare, because one account with nothing to pause was simpler.

4. Build one screen at a time

Switch to the stronger model for building. One screen per session, then commit.

Prompt: Build step 1 of PLAN.md: the Today page and the task list, with the D1 tables they need. Keep it simple, no UI library. Run the build when you're done and fix any errors. Then tell me how to run it locally.

After each screen, use it, then give notes the way you'd give notes on an edit:

"The late tasks should be at the top." "Show whose turn it is, not who created it." "This is too many clicks to tick a step."

Commit after every screen that works (git commit, or ask Claude Code to do it). If something breaks, you can always go back.

5. Run it on your laptop

Claude Code sets this up, but it usually looks like:

npm install
npm run build
npx wrangler dev        # app + API on http://localhost:8787, with a local database

Keep secrets in .dev.vars locally, and make sure .gitignore lists it. Never commit a key.

6. Put it online (about 30 minutes)

  1. Cloudflare dashboard → Workers & Pages → Create → Import a repository → pick your GitHub repo.
  2. Build command npm run build, deploy command npx wrangler deploy, production branch main.
  3. Create and deploy. D1 creates the database on the first deploy.
  4. Add your secrets (a long random sign-in secret, email keys) under Settings → Variables and secrets.
  5. Settings → Domains & Routes → Custom domain if you want it on your own domain.

From then on, every push to main redeploys it by itself.

7. Make it installable

Ask Claude Code for a web app manifest (name, icons, colours) and a small service worker. That's what makes "Add to Home Screen" (iPhone) or "Install app" (Chrome, Edge) appear, and it lets phone notifications arrive even when the app is closed. On iPhone, notifications need iOS 16.4 or later and the app added to the Home Screen first.

8. Run a security audit before real data goes in

This one matters. Your client list and invoices will live here.

Prompt: Do a security review of this whole project before I put real client data in it. Check sign-in and passwords, sessions, who can see what (every check must happen on the server, not just hidden buttons), SQL queries, secrets in the code or the git history, safety headers, and anything public that shouldn't be. List problems by severity, then fix them one at a time.

What ours ended up with, so you know what to aim for:

  • Passwords stored only as salted, slow hashes. 2-step sign-in with an authenticator app for the founders.
  • Accounts lock for 15 minutes after 8 wrong tries.
  • Sessions in cookies scripts can't read, ending on sign-out or password change.
  • Every permission checked on the server for every request.
  • Database queries that never mix typed text into SQL.
  • HTTPS only, can't be shown inside another site, and the browser only runs the app's own code.
  • An audit log of who changed access, passwords and deletions.

9. Use it for a week, then fix what annoys you

The first version will be wrong in small ways. Keep a note of everything that slows you down for one week, then fix the top three. That loop is where the tool becomes yours.

Lessons from building ours

  • The workflow doc did more than the code. Writing down how we work made our process clearer before a single screen existed.
  • Start smaller than you think. Today + Tasks first. We added money, drives and client logins only after we'd lived with the basics.
  • One platform beats three. One Cloudflare account runs the app, API, database and scheduled jobs. Fewer logins, fewer things to break.
  • One cron, not five. A single job every 30 minutes decides what to run (digests, reminders, alerts). Simpler to reason about.
  • You direct, AI builds. Claude wrote the code. Every decision about how the studio should work was ours.
